# Implementation plan: prune unused kernels and their release-specific material

**Deliverable:** a weekly vpsAdminOS maintenance job that makes **one fast-forward update of `staging`, containing one commit per retired kernel**, or makes no change. Maintenance opens no PR and needs no recurring manual review, auto-merge service or general repository-reference veto. Contributor PRs targeting `staging` run an advisory kernel-entry workflow only when GitHub's path filter matches. A release-specific livepatch or test is something to **remove with** its kernel, not a reason to keep that kernel. Reusable tests run against the stable selector. This plan supersedes the earlier proposed PR workflow. This is the accepted design and package-interface record. Source inspection used local Git; the current implementation/check status is in `state.md`, not implied by this plan.

## 1. Policy and metadata

Keep the public import `os/packages/linux/available-kernels.nix { lib }`, its two selectors, evaluated `kernels` shape and flake outputs. **Accepted storage layout:** one tracked regular Nix record `os/packages/linux/catalog/<K>.nix` per kernel; the facade derives `<K>` from each canonical filename and imports its record. Reject unexpected entries, symlinks, invalid/duplicate keys and missing selector targets, rather than silently hiding them. No hard-coded version list or Nix source editor. Each `kernels."<key>"` gets `dateAdded = "YYYY-MM-DD";` and optionally `keepUntil = "YYYY-MM-DD";`. No duplicated duration field: express a 90-day hold by adding 90 calendar days to the introduction date and recording the result. Both fields are strict Gregorian UTC calendar dates; a null, malformed/future addition, or hold before introduction is invalid. A hold can extend but never shorten the minimum.

At a supplied UTC instant with date `D`, the **only selection criteria** are:

1. `D > max(dateAdded + 30 calendar days, keepUntil if present)`. Added November 1: retained through December 1, first age-eligible December 2. A `keepUntil` of January 31 is inclusive.
2. The key is **neither** `stableKernelVersion` nor `unstableKernelVersion` (protect both resolved targets, even if identical).
3. No covered production host currently uses that key or its livepatched/native equivalent, with complete fresh evidence as defined below.

All matching entries are removed together; an invalid input or inconsistent edit fails the **run**, rather than adding a retention exemption. No searching the repository or downstream deployments to promote references into holds. Downstream users can set `keepUntil` or stick to an older OS revision when they need a future boot or rollback target not running now.

**Source basis.** At local vpsAdminOS `origin/staging` `b86287c10` there are nine keys, stable **6.12.118** and unstable **6.18.49**. `os/packages/linux/packages.nix` selects the default from `system.vpsadminos.enableUnstable`; `os/modules/config/kernel.nix` supports explicit selection. `flake.nix` exports `lib.availableKernels`, `lib.kernelVersions` and `ci-toplevel-kernel-*`. `.github/workflows/kernels.yml` builds the enumerated matrix. `skills/update-kernel/SKILL.md` points to `docs/os/kernel-updates.md`: registrations edit the catalog; there is no need for a second version updater. Dates are maintenance data, not inputs to Linux/ZFS builds. The existing kernel-build workflow is path-filtered and expensive; it is not the proposed required metadata check.

**Backfill once, then enforce.** At the approved baseline enumerate the keys. For each, verify the structural addition of that **version key** in vpsAdminOS Git history, comparing the introducing tree with its parent(s), following prior file shapes and the rename from `availableKernels.nix` (`77527f4c8`). Use the earliest proven introduction on the maintained branch's ancestry, inspect merges and distinguish removal/restoration from a different identity. Repins, releases of upstream Linux, moving a selector and editing an entry do not reset age. Convert the verified OS commit's **committer epoch** (`%ct`) to a UTC date. E.g. `71ae15a14` added `6.12.48`; `b1f9e8e5c` added `6.18.49` on 2026-10-12 UTC although authored in September. Review the complete `key → commit → date` table at implementation; don't guess on shallow or ambiguous history. No history walk in builds or normal retention runs.

Register new versions with their UTC day added, never a copied predecessor date. Validate the evaluated **whole** catalog: required field per key, permitted fields/types (including misspelled holds), dates and resolved selectors; surviving entries cannot change `dateAdded` outside the explicit migration. Extend `.overcommit.yml` alongside existing Nixfmt/RuboCop to validate the exact **index** (including staged companion files), not the unstaged checkout. Use the same checker in CI and before the maintenance commit. No fleet request at commit time. Inject a UTC evaluation date for date checks; preserve the existing project's hook and commit-message requirements.

**Split and staging invariants (A-owned).** Relocate the record expression, not its package inputs. Adjust relative Nix path literals for the extra directory level (e.g. `../zfs/zfs235-free-account.patch` → `../../zfs/zfs235-free-account.patch`); don't copy or rename inputs just to split the catalog. The `.110` version-private native patch has a separate C-owned relocation below; A adjusts the record to that final path and B adjusts the dedicated boot module in the same coordinated change. Preserve per-record `lib.kernel` config values, all immutable Linux/ZFS pins and patch ordering. Materialize the facade and its catalog/dependencies from the *same* Git tree with their repository-relative paths and modes. `--index` can use an isolated staged-tree projection; `--tree` and the base use their own committed projections, supporting the old inline catalog for migration comparisons. No staged import may read from an unstaged/untracked fallback. Exercise staged adds, staged deletes with an unstaged copy on disk, invalid staged values with valid working copies and vice versa. Compare base/candidate tuple values, resolved patch content and retained kernel/ZFS derivation/source identities for all keys with locked inputs in both builtin/external setups.

**A → hook/CI/D contract.** `python3 tools/kernel-entry-check.py check --as-of YYYY-MM-DD --base <commit-sha> (--tree <candidate-commit-sha> | --index)` validates the whole evaluated Nix catalog. Select exactly one of `--tree` and `--index`. Callers use the exit status, not a JSON/paths interface; diagnostics may name failing keys. D owns machine-readable planning outputs and paths. GitHub dispatch resolves the published candidate ref to the exact SHA, obtains `staging` itself and verifies base ancestry.

### Run kernel-entry validation on relevant PRs

The user chose event-level `pull_request.paths` and an advisory failure signal rather than an always-running, globally required PR check. `.github/workflows/kernel-entry-check.yml` starts no workflow for a docs-only PR targeting `staging`. On relevant PRs the existing read-only job validates the exact candidate merge tree and its first parent with the same offline catalog check as Overcommit. There is no runtime scope classifier. `workflow_dispatch` always runs full validation, including an empty diff; retain the staging lookup, exact-SHA/ancestry checks and `kernel-entry-correctness` job name for the weekly pruner's exact-tip admission. No branches, settings, permissions or pruning activation change.

The maintained event filter covers the catalog facade, the `catalog` and `kernel-specific` paths and their contents, the validator and its tests, `.overcommit.yml`, and the workflow itself. It does not list the shared ZFS patch separately: the validator checks patch references in the catalog, not the patch contents. The checker uses a fixed `lib.kernel` stub and does not import the lockfile. Extend the filter when adding an evaluation dependency outside those paths. Do not make this job a globally required GitHub status when unrelated PRs produce no check. The weekly writer's own full-dispatch check is separate from global PR enforcement.

Bounded A follow-up: replace the runtime classifier and its dedicated tests with the event filter, update the existing kernel guide, retain catalog tests, and check parsed YAML for the intended PR inputs and unconditional dispatch. Hosted trigger behavior and the weekly writer's branch rules remain distinct rollout checks. Previous always-emitted PR-status and global ruleset plans below are superseded where they conflict with this decision.

## 2. Live usage without production credentials

At vpsAdmin `origin/master` `4062a8da3`, `api/lib/vpsadmin/api/resources/node.rb` (`PublicStatus`), `api/models/node.rb`, and `api/spec/api/resources/node_read_spec.rb` agree with go-client `5934903`, `client/resource_node_action_public_status.go`: anonymous **GET `https://api.vpsfree.cz/v7.0/nodes/public_status`** returns one **unpaginated** list. Require successful HTTP and HaveAPI `status: true`, then `response.nodes`. Rows cover **active DB records of roles `node` and `storage`**, across locations/environments, including stale rows. Anonymous responses omit `id`; use the unique `fqdn`. `status` is false when the current status is absent or more than 120 seconds old. Use `status`, `last_report`, `type`, `hypervisor_type`, `fqdn` and `kernel`. `/nodes` is a different authenticated paginated index (`limit`/`from_id`), with kernel/status redacted for non-admins; don't silently substitute it. No admin token or API changes.

`libnodectld/lib/nodectld/{node_status,system_probes/kernel}.rb` report `/proc/sys/kernel/osrelease`. `6.12.113.1`, for instance, is a numbered livepatch on `6.12.113`. Match exact catalog keys and recognized canonical native-plus-numbered-release forms; protect all established equivalent targets in a collision. Never truncate arbitrary suffixes or compare version prefixes (`.11` is not `.110`). Unsupported grammar, ambiguous identity or a release absent from the current catalog is an error, not evidence of non-use. The separate `vpsfree-cz-configuration` `configs/node/kernels.nix` and `scripts/runtime_kernels.rb` use an ignored local runtime file, explicit overrides and SSH `uname`; do not treat these as a production census or reuse their truncation/error defaults.

Use bounded verified HTTPS, no redirect to another source or cached fallback. Require a nonempty array of unique returned identities, recognized role/host type, nonempty release, `status == true` and `last_report` within `[asOf − 120s, asOf]` for **every** covered host; likewise require the acquisition timestamp in that interval. An offline/maintenance machine is not excluded. Known last-seen versions are informative, but any missing/duplicate/stale/unsupported row, API/transport/schema failure or unexpected pagination blocks all writes. Never print response bodies or host identities in public logs.

**Population authority (user decision):** trust the public action for its returned active node/storage population. There is no separately configured or learned inventory, expected count or fingerprint. Canonicalize names only to validate identities and detect duplicates within a snapshot. An omitted host cannot be detected from the API alone; this limits the non-use claim to what the endpoint reports. Do not replace the removed safeguard with a second source, minimum fleet size beyond nonempty, login, manual reconciliation, or credentials. No raw host list or fleet snapshot in Git. Implementation transition from the prior digest-based design is specified in §7.

## 4. Plan, apply, verify, push

Use a small maintainer CLI with separate operations: `check` (index or tree, offline); `collect` (minimal timestamped projection of the one action); `plan` (pure); `apply` (apply only a verified plan to a clean disposable checkout). Give `plan` the base revision and evaluated catalog, explicit UTC instant and validated fleet projection. Do not require a separate inventory input. Sort decisions and owned paths bytewise. The same inputs yield the same reasons, keys and diff on replay with **no** network/implicit clock. Dry run by default; failure is distinct from an empty successful result. Intermediate full projections are private, short-lived. Log base, time, versions/reasons, aggregate coverage and changed paths, not identities or secrets.

1. Weekly cron on the trusted `vpsfreecz/vpsadminos` repo, optionally manual dispatch constrained to `refs/heads/staging`. Check out the current remote `staging` SHA **B** (not a caller-specified feature SHA). Serialize retention runs; other maintainers and scheduled update jobs can still advance the branch. Collect fleet evidence, plan on B. On any failure exit nonzero without a write; on zero candidates exit successfully without an empty commit.
2. Apply the exact deletion set as a **linear chain** in a clean detached checkout based on B. One scoped, normally hooked commit per kernel, with subject `os: retire kernel <version>`; C denotes the final tip. Independently prove every commit/parent/tree against the planned prefix and run the existing full offline checks on C (details in §6). Never publish a partial chain. A successful job on B (including the scheduler's own run) is **not** the required GitHub check on C.

   **Exact-SHA admission for direct pushes.** For normal human fast-forward integration, run `kernel-entry-correctness` on the exact published development head to be pushed (e.g. `workflow_dispatch` of the same read-only workflow on that ref). For a protected weekly push, publish the checked C on an isolated run-owned candidate ref without touching `staging`, dispatch the **same** check on that ref and verify GitHub reports success from the expected source **on C**. Dispatch using a bounded trusted orchestration job with `actions: write` only if needed; the check itself remains read-only. For dispatch, compare to the actual `staging` baseline and verify C descends from it, not an arbitrary caller-supplied baseline. Don't rely on a `GITHUB_TOKEN` candidate-ref push to trigger checks. If an acceptable exact-SHA check already exists, reuse it. No PR, standing actor bypass, synthetic success status or check on a different SHA. Prove the selected route works with the actual `staging` rules; if not, stop before enforcement/writes and resolve the rule conflict with the administrator. Ordinary human integrations still need their usual approval.
3. After the required check passes, immediately before the `staging` push, reread the remote tip; require it still equals B. Collect a **second**, newly acquired production snapshot, recompute on **B, not C**, at a fresh UTC instant; require the exact same eligible keys/owned changes as the tested commit, the existing within-run returned-row count check, and fresh valid evidence on the unchanged base (no external roster comparison). If anything differs or too much time elapses, discard this attempt; restart from a fresh base/plan later rather than force, blindly rebase or push a subset. Push C to `refs/heads/staging` with an ordinary **non-force** `git push`, never `--force`/`--force-with-lease`; a concurrent forward push makes C non-fast-forward and is rejected. Re-read the resulting ref/ancestry if the push result is uncertain; no blind retry. **No PR is opened.**
4. `contents: read` by default; `contents: write` only for trusted maintenance ref publication/FF, no PR permission, admin credential or production secret, no fork/PR code in that writer. A read-only prepare/check job can pass the checked commit via a run-local Git bundle, binding B/C and tree digest; the writer verifies every parent, intermediate tree and scoped diff before freshly planning/pushing. No network credentials during candidate code checks. Verify branch rules allow this exact automation principal's ordinary FF push. Don't disable protections or broaden tokens to evade an incompatible ruleset: leave report-only until ops configures permitted access. `.github/workflows/{daily-update,flake-update}.yml` provide direct-push precedents; `GITHUB_TOKEN`-authored pushes do not automatically trigger normal push workflows. Run the required offline checks in this workflow explicitly; preserve the existing scheduled kernel-build matrix. Verify imported action versions at implementation time.

The final double check narrows the race; a Git update is **not atomic** with a node boot. Ops should suspend the schedule or set calendar holds during transitions that can introduce an old kernel (including rollbacks). This isn't a per-run permission step. Report-only trials establish deployed response shape, normalization and population **before enabling writes**; direct weekly writes are the intended end state.
