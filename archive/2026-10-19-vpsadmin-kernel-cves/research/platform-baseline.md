## Shared tenant gates

- `api/models/vps_feature.rb` defaults **TUN, FUSE and KVM on**. PPP and LXC nesting are opt-in. `libnodectld/.../vps/features.rb` delegates `/dev/net/tun` (10:200), `/dev/fuse` (10:229), `/dev/kvm` (10:232), or optional `/dev/ppp` (108:0). Individual existing feature state and in-container device permissions remain runtime facts.
- The generated LXC config installs UID/GID mappings and includes `common.conf`, then `userns.conf`. The latter resets both capability drop/keep lists, retaining full capabilities **in the container user namespace**. Initial-user-namespace checks remain a boundary. `CAP_NET_RAW` in the owning network user namespace permits AF_PACKET; `CAP_NET_ADMIN` there permits network configuration, XFRM control and TUN creation.
- Default LXC seccomp is a short denylist: forced umount handling, `kexec_load`, `open_by_handle_at`, `init_module`, `finit_module`, `delete_module`. It does not block io_uring, perf, BPF, Landlock, CPU timers, keyctl or ordinary namespace calls. It can be overridden per container, so source defaults do not prove the runtime filter.
- Kernel module autoload is **disabled by default** in both historical producing recipe and current source. Many modules are explicitly preloaded: AF_PACKET, SCTP, nftables/ipset/IPVS and helpers, FUSE, OverlayFS, Ceph, CIFS, NFS, TUN, vsock and loopback transport. A compiled `m` alone proves neither availability nor exclusion. Modules outside the preload list require exact loaded-module/autoload evidence. Loading from a tenant cannot bypass initial-user-namespace module privilege and seccomp.
- For 6.12, source tunables set `kernel.unprivileged_bpf_disabled=0` despite the build's `CONFIG_BPF_UNPRIV_DEFAULT_OFF=y`; the BPF JIT and syscall are enabled. This is a source default, not a measured effective sysctl. The newer 6.18 policy differs and must not be applied to 6.12.
- The archived build has allocator freelist randomization/hardening, zeroing on allocation/free, stack initialization and stack protector, KASLR and FORTIFY. `CONFIG_HARDENED_USERCOPY=n` and AppArmor is disabled in this build. These protections change exploitation difficulty; none substitutes for a candidate's actual fix. No production exploitation inference follows from this source analysis.

## CIFS/SMB and Ceph supplemental gates

The seven CIFS leads (CVE-2026-64383/64384/64385/64386/64387, 64597 and 89633) have **no default tenant-created mount path established**. In exact historical Linux source, both `cifs_fs_type` and `smb3_fs_type` have `.fs_flags = FS_RENAME_DOES_D_MOVE`, **without FS_USERNS_MOUNT**. `fs/super.c` rejects a non-initial user namespace for a filesystem lacking that flag; full container-userns capabilities do not satisfy this gate. The inspected .113 downstream filesystem registrations also lack the flag. A preloaded CIFS module proves neither tenant mount permission nor any production mounted workload. Existing host-prepared/delegated CIFS mounts or an affected real host workload would make the candidates conditional, and remain unmeasured. An internal `fc->user_ns != init_user_ns` retry adjustment alone does not override the mount permission contract.

`CONFIG_CIFS=m` and `CONFIG_CIFS_ALLOW_INSECURE_LEGACY=y` in the exact archived build; the client module is explicitly preloaded. `disable_legacy_dialects` defaults false in source. Thus SMB1 is **compiled and not source-default disabled**, but candidate 89633 additionally needs a mount negotiating the legacy dialect (for example explicit vers=1.0), actual module parameter/policy, and the peer response prerequisite. This does not relax the initial-user-namespace mount gate. The SMB2 replay candidates need their own mounted client/peer/reconnect prerequisites; no default exposure claim follows from their Critical scores.

Ceph differs: exact `fs/ceph/super.c` filesystem flags include `FS_USERNS_MOUNT`, and Ceph/libceph are explicitly preloaded (`CONFIG_CEPH_FS=m`). Tenant namespace administrators can therefore prepare a controlled Ceph mount within this downstream source policy. CVE-2026-68159's malicious monitor/map path is a tenant-configurable filesystem/peer surface rather than a missing userns filesystem gate. Actual mount policy, server and workload are unmeasured; no current runtime mitigation or exploit success is asserted.

## Limits and next evidence
