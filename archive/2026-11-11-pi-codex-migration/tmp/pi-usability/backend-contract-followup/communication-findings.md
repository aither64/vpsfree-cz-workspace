## Findings

1. **“Queued for Pi” obscures the preserved delivery mode.** `portal/internal/web/static/app.js:298` labels every Pending Pi input this way. The actual request retains `steer` or `followUp`; `pi-runtime/src/session.mjs:261-276` calls public `Agent[delivery]` with the exact caller-owned user object while streaming, and uses literal `AgentSession.prompt` when idle. Enqueue returns Pending immediately after that insertion. Steer is consumed at an SDK processing boundary, after the active tool batch; it is not an interrupt of an executing tool. Follow-up waits until the agent would otherwise stop. Neither the generic label nor an enqueue acknowledgement proves acceptance or turn completion. This is a demonstrated presentation ambiguity, not proof of a wrong native delivery mode.

2. **Receipt enquiry has a five-second fallback cadence and temporarily gates sending.** `app.js:6964-6999` checks automatic Pending enquiries no more often than every 5000ms, calling the original message with `retry:true` at6980. At6977 it sets `messageDispatchInFlight` and invalidates idle/delivery readiness; this read-only enquiry therefore uses the mutation-busy UI gate. The first enquiry need not wait five seconds. Also, `app.js:5923-5935` can observe an exact accepted operation-ID/digest in the transcript earlier, so five seconds is not a universal minimum or proven measured delay. A slow enquiry can keep controls busy even though it cannot enqueue. Preserve same-ID semantics: `piruntime/input_delivery.go:46-76` returns the saved outcome or Unknown on a missing retry, never dispatches another input.

3. **Cross-session send is asynchronous behind a two-second dispatcher tick.** `communication/endpoints.go:330-352` saves the message and returns its view without dispatching. `web/communication.go:186-243` starts a 2s ticker and processes up to16 pending messages serially per pass under a20s pass context. New messages have no immediate wake in this path. A message arriving just after a tick can wait about2s before readiness/native work, and work ahead can add more; these are source scheduling properties, not measured timings for the user's send. Exact-target Pending becomes held/unconfirmed (`endpoints.go:485-503`) until the original captured tuple is looked up and proved Accepted (`endpoints.go:564-620`). That extra status delay is distinct from native queue-consumption time.

4. **Pre-enqueue work repeats substantial reads; its wall-time contribution is unknown.** Same-session team delivery checks caller and recipient in `web/pi_teams.go:281-300`. Each participant proves creation, tool policy, binds a snapshot and reads/projects transcript, plus target activity (`:361-418`). Cross-session `Pi.Prepare` uses that same participant path, then binds/activity-reads again (`web/pi_communication.go:37-61`). It is called for endpoint readiness (`communication/endpoints.go:243-256`), again before capture (`:467`) and again inside `Pi.Send` (`web/pi_communication.go:65`); this is before the final bind/capabilities/enqueue. `piruntime/controller.go:13-38` makes each managed call inspect the exact host and handshake; `manager.go:492-503` uses a sudo host-inspect subprocess. `Bind` reads a snapshot (`controller.go:123-129`); `session.mjs:151-168` walks the branch and hashes the serialized history. These are demonstrated repeated operations, but no per-stage timings were collected. Do not present them as the proven many-second cause or remove authority checks on this evidence alone.
