# 2026-06-08-vpsadmin-db-utf8mb

## Goal

Move the vpsAdmin MariaDB database, including production and test databases,
from `utf8mb3` to `utf8mb4` gradually, without service interruption and without
silent data truncation.

The first implementation target is an operator-facing set of vpsAdmin API rake
tasks that can inspect the live database, convert tables one at a time, ask
before each table by default, and resume naturally from database metadata.

## Affected repositories

- `vpsadmin`
  - API rake tasks under `api/lib/vpsadmin/api/tasks/db.*`.
  - Runtime/test database defaults in `nixos/modules/vpsadmin/api-app.nix`,
    `api/spec/support/db_setup.rb`, and
    `tests/configs/nixos/vpsadmin-services.nix`.
  - Core schema dump in `api/db/schema.rb` after final test/default switch.
- Future deployment follow-up, probably `vpsfree-cz-configuration`, may be
  needed only to pin and deploy the vpsAdmin revision. That is not needed for
  the rake-task implementation itself.

## Current State

Production connection config is generated by
`nixos/modules/vpsadmin/api-app.nix` with:

- `encoding: utf8mb3`
- `collation: utf8mb3_unicode_ci`

Test database setup also defaults to:

- `utf8mb3`
- `utf8mb3_unicode_ci`

The current core schema dump has tables using `utf8mb3_czech_ci`. Plugin tables
are not included in the core schema dump, so the conversion tasks must inspect
the live database through `information_schema` rather than relying on
`api/db/schema.rb`.

Runtime code has two explicit utf8mb3-era collations:

- `api/lib/vpsadmin/api/operations/authentication/password.rb` uses
  `COLLATE utf8_bin`.
- `api/lib/vpsadmin/api/resources/user.rb` uses
  `COLLATE utf8_unicode_ci`.

Local MariaDB 11.4.9 probes showed that these queries still worked when the
table was converted to `utf8mb4` but the connection remained `utf8mb3`.
These hard-coded collations must be updated during the final connection switch,
because an `utf8mb4` connection creates `utf8mb4` literals and MariaDB cannot
apply `utf8mb3` collations such as `utf8_bin` to those literals.

## Compatibility Findings

MariaDB documents `SET NAMES` as setting `character_set_client`,
`character_set_connection`, `character_set_results`, and
`collation_connection`; this is the behavior ActiveRecord/mysql2 reaches via
the configured `encoding` and `collation`.

MariaDB documents `utf8mb3` as UTF-8 for one to three bytes per character, and
`utf8mb4` as the same encoding plus four-byte supplementary characters. Existing
valid `utf8mb3` text therefore does not need different bytes when stored as
`utf8mb4`.

Local verification on MariaDB 11.4.9, which is the `mariadb` package version
reported by `github:NixOS/nixpkgs/nixos-26.05`:

- A table converted with
  `ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_czech_ci`
  remained queryable over a session using
  `SET NAMES utf8mb3 COLLATE utf8mb3_unicode_ci`.
- Plain comparisons, the current `COLLATE utf8_bin` login lookup, and the
  current `COLLATE utf8_unicode_ci` user search form all matched rows against
  the converted table.
- Mixed column comparisons between an old `utf8mb3_czech_ci` table and a new
  `utf8mb4_czech_ci` table also matched in the local probe.
- A supplementary character already stored in a `utf8mb4` table was returned
  as `?` over an `utf8mb3` connection. This is the important deployment guard:
  keep all application connections at `utf8mb3` during the table-by-table
  conversion, and do not allow separate utf8mb4 writers until the final
  connection switch.

The gradual approach is therefore viable, with this rule: converted tables can
run under the current `utf8mb3` connection as long as the system has not started
accepting or externally writing four-byte characters.

Emoji and other supplementary characters require both sides to be `utf8mb4`.
Converting a table to `utf8mb4` is not sufficient while the application
connection remains `utf8mb3`; the old connection cannot represent those
characters. After all tables are converted, the final connection switch to
`utf8mb4` should allow such data, subject to column byte limits.

## Data Safety

Existing string data should not be cut merely by converting from `utf8mb3` to
`utf8mb4`:

- `VARCHAR(N)` is limited in characters, so existing values that fit before
  still fit after conversion.
- Existing `utf8mb3` characters use the same UTF-8 byte sequences under
  `utf8mb4`, so existing `TEXT`/`MEDIUMTEXT`/`LONGTEXT` payload bytes do not
  expand during conversion.
- The tasks must not use `IGNORE`; conversion errors should stop the table
  rather than coerce or truncate data.

The real risks are operational/structural:

- Index key byte limits after `utf8mb4`, especially old row formats or unusually
  wide composite indexes.
- Maximum row size estimates after the charset change.
- Disk space and time for any table rebuilds.
- Future four-byte data can hit byte-limited text columns sooner than BMP-only
  data, although existing data does not grow.

The implementation should include a preflight report that inspects
`information_schema.COLUMNS`, `STATISTICS`, and `TABLES` for each table and
prints warnings/errors before any `ALTER TABLE` is run.

## Proposed Rake Tasks

Add namespace `db:utf8mb4`.

- `db:utf8mb4:status`
  - Print database default charset/collation.
  - List tables with engine, row count estimate, data/index size, table
    collation, text/varchar column charset/collation summary, and whether each
    table still needs conversion.

- `db:utf8mb4:preflight`
  - Validate target charset/collation availability.
  - Detect non-InnoDB tables, generated columns, fulltext/spatial indexes, and
    other shapes that may prevent non-blocking DDL.
  - Estimate index byte widths under `utf8mb4`.
  - Report current `@@version`, `@@sql_mode`, `@@character_set_%`, and
    `@@collation_%`.
  - Exit non-zero on hard risks unless `ALLOW_WARNINGS=1`.

- `db:utf8mb4:migrate`
  - Recompute remaining tables from live metadata each run; this is the resume
    mechanism.
  - Interactive by default: show table metadata and exact DDL, ask before
    altering each table, continue/pause after each table.
  - Non-interactive mode through `YES=1` or `INTERACTIVE=0`.
  - Filters such as `TABLES=users,tokens`, `SKIP_TABLES=...`, and
    `ORDER=size|name` for planned batches.
  - Default DDL should preserve the current collation family, e.g.
    `utf8mb3_czech_ci` to `utf8mb4_czech_ci`, and fall back to an explicit
    configured target only when requested.
  - Use explicit `LOCK=NONE` by default, while leaving `ALGORITHM` at MariaDB's
    default so MariaDB can choose the most efficient supported algorithm. On
    MariaDB 11.4 this can still choose an online table copy when needed.
  - If a table cannot be converted with `LOCK=NONE`, stop and report the table
    rather than silently falling back to a read-only or exclusive lock.

- `db:utf8mb4:finalize`
  - Verify no user tables/columns remain on `utf8mb3`/`utf8`.
  - Print or optionally run `ALTER DATABASE ... CHARACTER SET utf8mb4 ...`.
  - Verify no application SQL still hard-codes `utf8`/`utf8mb3` collations
    that would be invalid after switching the connection to `utf8mb4`.
  - Print the next deployment step: switch vpsAdmin connection config and test
    defaults to `utf8mb4`.

## Deployment Plan

1. Ship the rake tasks while leaving production and tests configured for
   `utf8mb3`.
2. Run `db:utf8mb4:preflight` in production and record the table order.
3. Convert tables in batches with `db:utf8mb4:migrate`, keeping services
   running. Pause simply means stop between tables; resume reruns the task.
4. After all tables and relevant column-level collations are `utf8mb4`, change
   defaults and connection configuration to `utf8mb4` in a second commit:
   - production `database.yml` generation,
   - test DB defaults,
   - integration-test DB initialization,
   - schema dump.
5. Deploy/restart all vpsAdmin API/supervisor/webui processes together for the
   final connection switch. Mixed old/new connections against `utf8mb4` tables
   are mostly workable, but old `utf8mb3` connections cannot faithfully handle
   new four-byte data.

No vpsAdminOS node-wide coordinated update is expected. This is a vpsAdmin
database/application deployment concern.

## Rollback Notes

- During table conversion, rolling back application code is safe because the
  old `utf8mb3` connection can read/write BMP-only data in converted tables.
- If an `ALTER TABLE` is killed, MariaDB documents rollback behavior for the
  DDL; it can be slow, so operators should prefer stopping between tables.
- MariaDB 11.4 can perform most copy-based `ALTER TABLE` operations with
  `LOCK=NONE`, so reads and writes can continue during the main copy phase.
  There are still short exclusive metadata locks at the start and end, and
  long-running transactions touching the table can delay those phases.
- After the final connection switch, rollback to old application config remains
  technically possible only if no four-byte data has been accepted. Once
  supplementary characters are stored, old `utf8mb3` connections can return
  replacement characters and should not be used.

## Decisions

- Production will use the MariaDB package from NixOS 26.05; Nix reports this
  as MariaDB 11.4.9.
- Treat charset migration and project-default collation as separate decisions.
  Preserving existing collation families
  (`utf8mb3_czech_ci` -> `utf8mb4_czech_ci`,
  `utf8mb3_unicode_ci` -> `utf8mb4_unicode_ci`) is the lowest-risk production
  migration because it avoids changing current comparison/sort behavior. It is
  not an ideal neutral upstream default.
- For project defaults and regenerated `schema.rb`, prefer a neutral
  `utf8mb4` collation such as `utf8mb4_unicode_ci` unless a separate review
  intentionally chooses a newer UCA collation. Avoid `utf8mb4_general_ci` as a
  new default because it is faster/older but less linguistically correct.
- If production storage is preserved as `utf8mb4_czech_ci` while `schema.rb`
  becomes neutral, document the intentional divergence and keep tests for
  collation-sensitive behavior. If exact production/test parity is preferred,
  defer neutralizing `schema.rb` to a separate collation-normalization change.
- Emoji/user-data support is expected only after the final phase, when both
  storage and application connections use `utf8mb4`.
- There are no external writers; only vpsAdmin services write to the database.
- Use native MariaDB online DDL only. Do not prepare a shadow-table
  online-schema-change fallback.
