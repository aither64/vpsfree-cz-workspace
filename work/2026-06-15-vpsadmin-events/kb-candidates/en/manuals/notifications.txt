====== Notifications ======

The vpsAdmin notification system processes events and sends them to receivers according to routes. Open it from the <vpsadmin-nav id="notifications.open">main Notifications menu</vpsadmin-nav>.

The basic flow is **event → route → receiver → target**:

  * an **event** describes what happened and contains a type, severity and additional data,
  * a **route** selects events by type and optional matchers,
  * a **receiver** defines what should happen to a selected event,
  * a **target** is a specific e-mail address, webhook, telephone number or Telegram account.

===== Routes =====

Manage routes at <vpsadmin-nav id="notifications.routes.open">Notifications → Routes</vpsadmin-nav>. Routes are evaluated in order. A route can continue to another matching route, contain child routes, or expire after its first use. Default routes provide normal delivery to the primary e-mail address; you can add custom routes or select the **Mute** receiver.

{{:en:screenshots:vpsadmin:notifications:routes.png?900|Notification routes}}

Route matchers compare event fields. Every matcher on one route has to match. When a route selects a specific event type, its field and operator choices adapt to the data declared by that type.

===== Receivers and contacts =====

A receiver at <vpsadmin-nav id="notifications.receivers.open">Notifications → Receivers</vpsadmin-nav> groups one or more targets. One receiver can therefore send an e-mail and call a webhook at the same time. The **Default** target uses the account's current primary e-mail address. Add other e-mail addresses as custom targets; they have to be verified before use.

{{:en:screenshots:vpsadmin:notifications:receiver.png?900|Receiver configuration}}

A receiver can be disabled without removing its routes. The **Mute** receiver creates no outgoing delivery. An event that reaches normal event processing remains in the event log; muting an OOM report at the ''raw'' stage, described below, is a special case.

===== Practical examples =====

The following examples use custom receivers and routes. Enable **Continue** when an event should also pass through later matching routes. Put mute routes before delivery routes and leave **Continue** disabled on them.

==== Route by event role ====

The ''roles'' field is a list of contact roles for which the event is intended. ''account'' identifies the account-management contact and ''admin'' the system administrator. One event can carry both roles, so use **contains list item**, not a comparison of the whole list.

First create and verify two e-mail targets, then add them to **Account contact** and **Administrator contact** receivers. Create these routes:

^ Event type ^ Field ^ Operator ^ Value ^ Receiver ^ Continue ^
| //any// | ''roles'' | contains list item | ''account'' | Account contact | yes |
| //any// | ''roles'' | contains list item | ''admin'' | Administrator contact | yes |

{{:en:screenshots:vpsadmin:notifications:example-role-routing.png?900|Routing by event role}}

**Continue** lets an event with both roles reach both contacts and preserves any other matching delivery routes.

==== Mute selected OOM and incident reports ====

Use the **Mute** receiver and two separate routes. This example mutes OOM reports for VPS ''123'' from user scopes, and incident reports for the same VPS with codename ''abuse-feed'':

^ Event type ^ Matchers (all must match) ^ Receiver ^ Continue ^
| ''vps.oom_report'' | ''vps_id == 123''; ''stage == raw''; ''cgroup =* /user.slice/*.scope'' | Mute | no |
| ''vps.incident_report'' | ''vps_id == 123''; ''codename == abuse-feed'' | Mute | no |

The ''=*'' operator means **matches glob**. The cgroup value is the full path without a ''/sys/fs/cgroup'' prefix. Incident codenames are assigned by their source; copy the exact value <vpsadmin-nav id="notifications.event-route-matches.open">from the detail of a real incident in the event log</vpsadmin-nav>.

{{:en:screenshots:vpsadmin:notifications:example-mute-oom.png?900|Muting OOM reports by cgroup}}

The ''stage == raw'' matcher is essential for OOM reports. It evaluates the route as each report arrives and marks the report ignored, so it does not enter a later notification batch. This transient ''raw'' event is not stored in the event log. Without the ''stage'' matcher, the route could mute the resulting notification but would not prevent the report from being batched.

Put mute routes before general delivery routes and leave **Continue** disabled. Use **Test event** and the route hit count to check the configuration; use values from a real OOM report when checking a cgroup path.

==== Send monitoring and incidents to Telegram ====

Create a **Telegram** target, open its pairing link in a private chat with the bot, and press Start to complete pairing. Add the paired target to an **Operations Telegram** receiver.

Create two routes:

^ Event selection ^ Receiver ^ Continue ^
| pattern ''monitoring.*'' | Operations Telegram | yes |
| type ''vps.incident_report'' | Operations Telegram | yes |

{{:en:screenshots:vpsadmin:notifications:example-telegram.png?900|Telegram for monitoring and incident events}}

The pattern catches every event type starting with ''monitoring.''. The second route adds incident reports. **Continue** keeps the default e-mail routes working as well. Re-pairing pauses Telegram delivery until the bot confirms the new pairing.

==== Send SMS on account or VPS suspension ====

Create an **SMS** target, enter the number in international E.164 format (for example ''+420123456789''), send a verification SMS and enter its code. Add the verified target to a **Suspension SMS** receiver.

^ Event type ^ Receiver ^ Continue ^
| ''user.suspended'' | Suspension SMS | yes |
| ''vps.suspended'' | Suspension SMS | yes |

{{:en:screenshots:vpsadmin:notifications:example-sms.png?900|SMS on account or VPS suspension}}

The first route reports suspension of the whole account, while the second reports suspension of an individual VPS. **Continue** preserves the normal e-mail notifications.

==== Webhook on VPS resource changes ====

Create a **Webhook** target with a public HTTPS URL and a random HMAC secret. Add it to a **Resource-change webhook** receiver, then create a route for ''vps.resources_changed'' with **Continue** enabled.

{{:en:screenshots:vpsadmin:notifications:example-webhook.png?900|Webhook for VPS resource changes}}

vpsAdmin sends a ''POST'' request with a JSON body and these headers:

  * ''Content-Type: application/json'',
  * ''User-Agent: vpsAdmin notification dispatcher'',
  * ''X-VpsAdmin-Event: vps.resources_changed'',
  * ''X-VpsAdmin-Delivery: <delivery ID>'',
  * ''X-VpsAdmin-Signature-256: sha256=<HMAC>'' when the target has a secret.

HMAC-SHA256 is calculated from the unmodified request-body bytes. This small server verifies the signature, prints the received JSON and returns a successful ''204'' response. It listens on localhost only; put it behind a public HTTPS reverse proxy for real use.

<code python>
import hashlib
import hmac
import json
import os
from http.server import BaseHTTPRequestHandler, HTTPServer

SECRET = os.environ["VPSADMIN_WEBHOOK_SECRET"].encode()


class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers.get("Content-Length", "0"))
        body = self.rfile.read(length)
        expected = "sha256=" + hmac.new(
            SECRET, body, hashlib.sha256
        ).hexdigest()
        received = self.headers.get("X-VpsAdmin-Signature-256", "")

        if not hmac.compare_digest(received, expected):
            self.send_response(401)
            self.end_headers()
            return

        print(json.dumps(json.loads(body), indent=2))
        self.send_response(204)
        self.end_headers()


HTTPServer(("127.0.0.1", 8080), Handler).serve_forever()
</code>

Run it with the same secret configured on the target:

<code>
VPSADMIN_WEBHOOK_SECRET='a-long-random-secret' python3 webhook.py
</code>

The target must be reachable from vpsAdmin. Private, local and link-local addresses are normally rejected, so do not use ''127.0.0.1'' or a home-LAN address as the target URL. Any ''2xx'' response is successful. Failed deliveries may be retried, so make processing idempotent using ''delivery.id'' or the ''X-VpsAdmin-Delivery'' header.

===== Time intervals =====

Define reusable intervals at <vpsadmin-nav id="notifications.time-intervals.open">Notifications → Time intervals</vpsadmin-nav>. Every interval has a name, an IANA time zone (for example ''Europe/Prague''), and one or more specifications.

{{:en:screenshots:vpsadmin:notifications:time-interval.png?900|Time interval configuration}}

Within one specification, every filled dimension must match. Multiple ranges in one dimension are alternatives, and multiple specifications are also joined with logical **OR**. The available dimensions are:

  * times in ''HH:MM-HH:MM'' format, inclusive at the start and exclusive at the end,
  * weekdays written in English, for example ''monday-friday'',
  * days of month; negative values count from the end (''-1'' is the last day),
  * months and years as numbers or ''start:end'' ranges.

Time and weekday ranges cannot wrap. Split an overnight interval into two specifications, for example ''22:00-24:00'' and ''00:00-06:00''; when weekdays are constrained, assign the second part to the following day.

===== Active and mute route intervals =====

Assign an interval to a route at <vpsadmin-nav id="notifications.route-time-intervals.open">Notifications → Routes → edit route</vpsadmin-nav>, using **Active interval** or **Mute interval** mode.

{{:en:screenshots:vpsadmin:notifications:route-time-intervals.png?900|Interval assigned to a route}}

  * With no active interval assigned, the route's active time is unrestricted.
  * With multiple active intervals, a match of any one is sufficient.
  * A matching mute interval always suppresses delivery.
  * An interval gates only that route's receiver. Child routes are still evaluated and the route's continue behavior is preserved.

An account can define at most 50 intervals. An interval can contain at most 20 specifications and each dimension at most 20 ranges. At most 20 intervals can be assigned to one route. An interval in use cannot be deleted until it is unassigned from every route.

===== Checking delivery =====

Inspect the result at <vpsadmin-nav id="notifications.event-route-matches.open">Notifications → Event log → event detail</vpsadmin-nav>. The detail shows matching routes, the time-interval state and the evaluation snapshot at the event timestamp. ''inactive'' means no active interval matched; ''muted'' means a mute interval matched.

{{:en:screenshots:vpsadmin:notifications:event-suppressed.png?900|Event suppressed by a time interval}}

Use **Test event** to verify a new configuration safely without waiting for a real incident.
