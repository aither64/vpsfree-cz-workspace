====== Notifications ======

The vpsAdmin notification system turns events into e-mail, SMS, Telegram, or
webhook deliveries. Open it from the
<vpsadmin-nav id="notifications.open">main **Notifications** menu</vpsadmin-nav>.

The basic flow is **event → route → receiver → target**:

  * an **event** describes what happened,
  * a **route** selects events and decides whether routing continues,
  * a **receiver** describes who or which integration should be notified,
  * a **target** is a concrete e-mail address, telephone number, Telegram chat, or webhook endpoint.

===== Routes and matchers =====

Manage routes at <vpsadmin-nav id="notifications.routes.open">**Notifications
→ Routes**</vpsadmin-nav>. Routes at the same level are evaluated from top to
bottom. Every matcher on one route must match.

Choose **Event type** for one exact type. Use **Event type pattern** for a
shell-style glob such as ''monitoring.*''. Leave both empty only when the route
is intended to match all event types. The **Event types** page lists available
types and their fields.

**Continue: yes** lets later sibling routes evaluate the same event. This is
useful when, for example, both Telegram and e-mail should receive it.
**Continue: no** stops at that route; mute routes normally use this setting.
Subroutes are evaluated after their parent matches, independently of the
parent's **Continue** setting.

===== Targets and receivers =====

Manage concrete destinations at
<vpsadmin-nav id="notifications.target-form.open">**Notifications →
Targets**</vpsadmin-nav>. Custom e-mail and SMS targets must be verified and
Telegram targets must be paired before they can receive notifications.

Manage receivers under
<vpsadmin-nav id="notifications.receivers.open">**Notifications →
Receivers**</vpsadmin-nav>. A receiver can contain several targets. A route
points to the receiver, not directly to an address. The built-in **Mute**
receiver has no delivery target and suppresses matching events.

===== Event grouping =====

Grouping is useful when many related events arrive in a short burst. Instead
of sending a message for every event, vpsAdmin collects them and sends a
summary. The default OOM-report route uses grouping by ''vps_id'', so reports
from one VPS are summarized together and reports from different VPSes stay
separate.

Grouping is configured separately on an existing route at
<vpsadmin-nav id="notifications.route-grouping-form.open">**Notifications →
Routes → edit route → Notification grouping**</vpsadmin-nav>:

  * **Group by fields** contains comma-separated scalar event fields. Their values identify a group. Leave it empty to put all events matching the route into one group.
  * **Initial wait** is how many seconds the first event waits so more events can join a new, idle group.
  * **Repeat interval** is the minimum delay before another summary from the same still-active group.

For an exact event type, use fields listed for that type on the **Event types**
page. Pattern and catch-all routes can use only common fields accepted by the
form. Grouping belongs only to that route and is not inherited by subroutes.
Muted, skipped, and time-suppressed events do not enter a group.

The group is defined for the route and receiver before individual delivery
actions are sent. If one receiver has e-mail, Telegram, and webhook targets,
each action receives the same set of grouped events. It is not three
independently timed groups.

{{:en:screenshots:vpsadmin:notifications:grouping-route.png?900|Grouping settings on an OOM-report route}}

Open
<vpsadmin-nav id="notifications.groups.open">**Notifications → Notification
groups**</vpsadmin-nav> to inspect open, overdue, idle, and historical groups.
A group detail shows its route, receiver, grouping labels, timing, pending
events, and deliveries. Individual deliveries remain visible in the event
detail.

===== Time intervals =====

Define reusable intervals under
<vpsadmin-nav id="notifications.time-intervals.open">**Notifications → Time
intervals**</vpsadmin-nav>. A time interval is useful for:

  * silencing alerts outside working hours,
  * sending work-hours and on-call notifications to different people or teams,
  * limiting a route to a recurring maintenance window,
  * expressing complementary schedules with separate routes.

Each interval has an IANA time zone and one or more specifications. Fields
within one specification use logical **AND**; multiple ranges or specifications
are alternatives.

{{:en:screenshots:vpsadmin:notifications:time-interval.png?900|Time interval configuration}}

Assign an interval at
<vpsadmin-nav id="notifications.route-time-intervals.open">**Notifications →
Routes → edit route**</vpsadmin-nav> as an **Active interval** or **Mute
interval**. With no active interval, the route has no active-time restriction.
A matching mute interval suppresses that route.

{{:en:screenshots:vpsadmin:notifications:route-time-intervals.png?900|Time interval assigned to a route}}

===== Event log and delivery checks =====

Inspect routing at
<vpsadmin-nav id="notifications.event-route-matches.open">**Notifications →
Event log → event detail**</vpsadmin-nav>. The detail shows matched routes,
time-interval state, deliveries, and the routing snapshot captured when the
event occurred. ''inactive'' means no active interval matched; ''muted'' means
a mute interval matched.

{{:en:screenshots:vpsadmin:notifications:event-suppressed.png?900|Event suppressed by a time interval}}

**Test event** checks routing without causing a real suspension or incident,
but its notification delivery is real and may send e-mail, Telegram, SMS, or a
webhook request.
