# 2026-11-01-api-doc-language-settings

## Goal

API documentation in HTML generated by HaveAPI servers/ruby should be localized in Czech / English. Use the appropriate language for the users browser while defaulting to English. The UI must allow the user to choose a language, add this to the Settings dropdown menu above Theme control. Client code examples should still be in English, but comments can be localized. Suggest a solution.

## Affected repositories

- HaveAPI (`servers/ruby` HTML documentation renderer and browser assets).
- Include built-in HaveAPI protocol documentation linked from the online API
  reference (user addition during investigation).
- User authorized implementation after reviewing the proposal. Scope includes
  runtime/UI localization and linked internal documentation. Later user direction
  explicitly authorizes HaveAPI/master integration; the temporary preview is
  separately authorized and retained.

## Approach

- Architect `architect0` inspects the current renderer, Settings/Theme controls,

- Implementers own runtime/UI and article/source-layout/packaging packages under

  keep session and preview open after integration.

## Decisions

- Support Czech (`cs`) and English (`en`), defaulting to English when browser
  preferences do not select a supported language.
- Place the language control in Settings above Theme.
- Show only English and Česky (latest user wording); browser detection applies until a user saves
  an explicit choice. Do not present an Automatic option.
- Preserve executable examples in English; explanatory comments may be translated.
- User visual feedback explicitly requires localized generated comments, including
  authentication examples, with noncomment code unchanged.
- With JavaScript, show only the language select and switch on change; retain
  the submit button only as the supported no-JS fallback. Czech sidebar label: Jazyk.
- Existing i18n:health is the translation guard the user remembered; retain it
  and extend recognized calls only as needed for comment translations. No new
  arbitrary-literal classification subsystem is requested.
- User explicitly requires framework-owned generated Go/Rust/TypeScript client
  documentation prose translated too, superseding the prior English adapter-prose
  boundary. Enable actual profiles in the temporary preview for visual review.
  Package names, commands, API symbols and sample data remain unchanged.
- Distinguish framework-owned UI text from descriptions supplied by API authors.
- Translate linked protocol prose too, preserving protocol identifiers, wire
  values and executable examples; maintain language across reference/guide links.
- Use symmetric article sources under `doc/en/` and `doc/cs/`; user explicitly
  permits moving the English files. Preserve public routes and fragment IDs.

examples stable. A new cookie can be ignored by old versions; the moved article
layout ships and rolls back with the complete server package. No database or
protocol migration, coordinated client update or deployment is required here.
