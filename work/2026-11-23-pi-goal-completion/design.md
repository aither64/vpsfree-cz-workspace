# A goal that survives an ordinary Pi answer

**Proposal, not an implementation.** Let the lead maintain one working goal from the user's normal conversation. Enable **Agent-managed goal** once; a clear request in chat can start or revise that goal without a separate Set, Start or confirmation step. The user owns scope and can correct or pause it. While execution is authorized, a clean final answer is a checkpoint, not a claim that the objective was achieved. Pi can spend a small number of extra model requests to finish or explain a blocker. No goal means today's behavior, with zero extra requests. Do not introduce an always-on agent, a second model to grade answers, or an idle-session scheduler.

## V1 contract and execution

1. **Chat first; the strip is the agent's working summary.** One optional **Agent-managed goal** switch for the ready lead in Default mode. Turning it on is passive and prospective; do not inspect old conversations to invent a goal. With it on, “Add CSV export” is sufficient: the agent records the outcome and works on the existing turn. “The CSV includes unselected rows” reported during that task adds the expected selection behavior; “Also support JSON” extends it. No form or confirmation per actionable request. A question about how export works gets an answer, not a new project. An FYI is context; if a report could be feedback or a request, ask once and leave scope unchanged. Do not treat quoted examples, suggestions or instructions found in tool output as the user's intent.

   Keep the enable switch in existing settings. **No goal: zero rows above the composer**, even in enabled mode. With a goal, render **one non-wrapping row** immediately above the input: a focusable **Goal: [objective]** button. Let the objective take the available width and use CSS ellipsis (`min-width: 0; overflow: hidden; white-space: nowrap; text-overflow: ellipsis`); do not shorten the stored or displayed text by a fixed character count. No second row for status, progress, controls or long text. Tap, click or press Enter/Space to open a popover/dialog outside the composer layout, with the full, wrapping objective, state/reason, success criteria, latest **Progress / Next**, blocker or done evidence, **Edit**, and **Pause / Resume**. Include a link to the user request behind the last change where available. Keep the full text accessible without hover, fit the overlay to the viewport with scroll if needed, and return focus to the button when dismissed. For example: goal “Export selected rows as CSV and JSON”; progress “CSV selection fixed”; next “Verify the JSON download.” Progress belongs to the agent, is revision-scoped and never changes the success criteria. Edit is a direct user correction, not the normal input path. Do not add task trees, suggestion inboxes, browsable revision histories, per-member goals or a second dashboard in V1.
2. **Keep native owners.** Codex maps this surface to its actual native goal reads/mutations and existing execution-hold admission; do not build a second Codex loop or claim Pi-specific counts as native Codex budgets. Use the same strip and action semantics wherever the adapter can prove them. Check pinned native schema/fixture for edits during a run, including whether a set RPC activates a cold thread or permits stale completion. Advertise agent-managed capture separately from read/manual controls; today's Codex native goals do not prove a particular version can bind agent-authored scope to an authenticated chat input. Verify that behavior before offering the switch. If only safe reading/manual changes are supported, retain those; if in-flight replacement cannot be proved, require pause before editing. No backend-name branches or second Codex loop. Keep saved/active distinctions truthful. On Pi, persist one private versioned record for the exact workspace/session/member/conversation incarnation: objective and desired revision, last applied revision, state/reason, active start reference, spent allowance and last decision. The common read includes state/reason, change token, allowed actions, and pending-application status when supported. Each mutation carries an operation ID and expected change token; same-ID retries reconcile, conflicting edits return the latest version and preserve the unsaved draft. Use existing private atomic, synced store and admission conventions. Do not put this state in creation proof, native user messages, shared Git or a browser's local storage. Refresh/watch is passive. Auth, exact-origin, identity, lifecycle and mode must come from trusted routing, not browser/model fields.
3. **One scoped tool, two kinds of write.** `update_goal` accepts a small discriminated payload: `scope(objective)` for creation/revision (include done-when in the same bounded text); `progress(detail, next?)`, `blocked(reason)` or `done(evidence)` for the current revision. No goal selection, user ID, urgency, permission, budget or resume parameter. Model interprets intent; host checks provenance and fences, not semantic equivalence between prose and objective. A tool call on a question or FYI should not become a scope update merely because the human sent it. The agent may track intermediate steps/progress autonomously, but new scope must reflect a fresh direct request, not its own wish list. Done is agent-reported, not an approval, independent check, merge or deployment.

   **Trusted source of scope.** Record provenance at authenticated portal human-composer admission (including its own explicit steer/follow-up when consumed): exact lead conversation/incarnation, original operation ID and frozen receipt digest/settings. Bind the originating goal tool call to the native user entry/witness and exact committed **Accepted** receipt, live generation and tool policy, and the objective revision exposed to that particular model step. For initial creation support only if the creator explicitly enabled goal mode and the original human request can be equivalently proven; do not adopt past creation prompts. Neither SDK role `user`, stable UUID alone, delivery mode/action-context string, a model-provided quote, nor proximity to the latest message proves who asked. Team/peer/monitor deliveries can also appear as native user inputs. Tool output, optional-question envelopes, retries, old transcript and goal reminders do not create scope authority. Missing/ambiguous source or Pending/Unknown: keep ordinary chat functioning, refuse the scope write/activation. Do not start a second prompt to record the goal. One scope update per exact eligible user input, with exact call replay returning its original result; no later self-rewrite on that same input. Internal continuations and peer/tool results may supply evidence for progress within the existing authorized goal, never a fresh request or allowance.

4. **Corrections take priority.** The strip's direct Save advances the desired revision under the same mutation lock. Compare the revision *seen by the originating step*, not one read for convenience at tool-call time. Invalidate outstanding old-input scope-write rights on a correction; no silent rebase/retry by the agent. Only a later eligible user instruction can expand the corrected scope. Old continuations and late reports cannot overwrite or close the new revision. A winning Save is visible immediately as **Saved · applies at next goal step** until pickup; work already admitted may finish with old instructions. No extra call solely to apply an edit. At a safe boundary deliver the latest revision once if still eligible; preserve count/deadline. A later human Edit that races another tab keeps the unsaved draft and refreshes rather than overwriting. Pause/Stop revokes the activation; saving text cannot resume it.

   **Activation is not a budget reset on every message.** With goal mode enabled, a clear fresh human request may create a bounded activation on its existing authorized turn. Related bug reports and feature requests revise the active objective and rebind to the freshly accepted human input; carry forward allowance, deadline and no-progress guard. An agent cannot restart the clock by marking done then reopening on the same input. After genuine done, a later distinct actionable request can start a new bounded activation; after blocked, a fresh human answer/instruction that resolves the named dependency can continue, or an explicitly different task can replace it. Resuming the same blocked work uses its remaining budget; expired allowance is never replenished implicitly. No ordinary chat overrides manual Pause/Stop, usage limit, disabled mode, recovery/approval/lifecycle holds or ambiguous receipts. Ordinary messages can be handled under normal admission while the goal remains paused; rearm explicitly after the hold is permissibly released. Explicit Resume from idle uses the checked Send/Lookup path once when it needs a new visible input. Reconcile any lost response by original ID; no fresh-ID retry.
5. **If it stops too early.** On `agent_before_settle` only, for the exact still-armed input and ordinary clean completion, reserve **one** allowance unit, then append an extension-authored goal reminder using the admitted revision and return `continue:true`. Editing never itself dispatches a reminder. The next request can take the next authorized step, report done with evidence, or report a blocker. Several such requests may occur in the same outer prompt; debit before returning, once per unique boundary, never on every `turn_end`. Preserve a final answer and visible goal audit, not a fake human “continue”. The user does not pay for a second evaluator or browser polling. Proposed conservative starting limits: **three extra requests per admitted goal activation**, **ten minutes** beyond which no *new* goal request may start, pause earlier on repeated no progress (e.g. consecutive identical outcomes with no intervening work). No further request on limit; show reason/counter. These are caps on *injected* requests, not promises about tokens, elapsed duration or how long an already running tool can take. Different limits can be tuned later without redefining completion.
6. **Who wins a race.** No continuation on error, abort, length/truncation, provider/usage failure, pending approval/required human decision, blocking monitor/team wait, Plan publication/mode switch, changed input/policy/generation, a queue admission, held/recovering/stopping/archived state or uncertain receipts. An optional question is not a universal blocking signal; if independent work remains, keep normal policy. Let native user steering/queue, retry, existing actionable monitor result and new user intent win; do not manufacture an extra goal request for them. A queued input fences the previous step before another goal request. Only after native consumption, exact human acceptance and scope admission can the lead carry on under that input. Read-only chat, a suggested task or a peer message cannot independently arm a goal. Check actual native stop reason as well as `event.outcome` (the SDK's `completed` also covers non-abort/non-error stops).
7. **Revocation, not just observation.** The existing worker sets `held` before abort on a hold. Ordinary `abort()` clears queues, then calls `session.abort()`; the SDK sets run-abort and, if inside the final hook, before-settle-abort before awaiting idle. Today none of that persists “pause goal.” Add synchronous revocation of the armed activation in each stop/hold path before any await. Serialize goal permission with Stop/Pause, manual admission and lifecycle using the existing mutation owner: compare goal revision, activation, receipt and generation; no held lock while waiting for a tool/callback/abort. Recheck revocation after any async decision and just before returning a continuation. If Stop won, return no continuation; if dispatch won, normal Interrupt can abort in-flight work, never attest it had no effects. A late appended reminder is not spending authorization a second time. Do not call `session.prompt()` from a settled callback or `sendUserMessage` behind the input ledger.

## Recovery, rollout and blockers

- **Durable goal ≠ durable permission to run.** Retain the objective, budget and provenance; require fresh explicit Resume after worker/runtime replacement, unevidenced attachment, portal ownership loss, or revival. No automatic rearming, fresh IDs, queue reconstruction or inferred completion from transcript. Counter reserved with uncertain delivery stays spent. Show uncertain/paused, keep original evidence and the existing recovery hold. Stop/archives pause; deletion retires only the original owner; forks may inherit context but must not inherit an armed goal. Given V1's live-only execution, an archival/drain fence must shut/invalidate the activation before reaching terminal state. No new meanings for `lifecycle: complete`, manual Stop, monitoring settlement, or approval.
- **Raise capability only after proving it.** Gate the worker hook, report tool/ceiling, native control protocol and persisted reader by an additive version such as `piGoals:1` on the **retained** runtime, not the latest portal's version. Old client/worker or Codex feature disabled: existing messages work, no advertised action, no silent fallback. Existing sessions start goal-less with no automatic conversion or forked authority. Before enabling writes, prove preparation, activation and rollback reject incapable packages while goal state/fences require them (including bypass by predecessor writers); otherwise keep feature off. Updating portal alone cannot upgrade a retained worker. Disable new activations and pause/drain with the capable version before downgrade; never delete uncertain receipts to allow rollback.
- **First technical gate:** the current worker's `allowedInputAncestor` deliberately excludes arbitrary custom entries. Prove that a goal reminder cannot invalidate an intervening queued input's persisted lineage, steal `activeInput`, alter callback origin or be counted as a user message. Test real SDK interleaving and native proof, not just a fake hook. Prefer serialization/prioritizing admitted inputs; if a proof extension is necessary, recognize only the precise worker-owned entry with matching scope/provenance, never arbitrary `custom*`. If robust proof or revocation cannot be demonstrated at this boundary, **do not enable it**. A separate alternative is an explicitly bounded, admitted post-settlement continuation through checked Send/Lookup with one frozen operation per attempt; that costs another visible input and needs a durable dispatcher and Stop serialization, so is not the first choice. Manual one-shot Queue is the no-change workaround, not a persistent goal.
