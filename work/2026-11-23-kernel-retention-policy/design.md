# Implementation plan: prune unused kernels and their release-specific material

**Deliverable:** a weekly vpsAdminOS maintenance job that makes **one fast-forward commit directly to `staging`**, or makes no change. Maintenance opens no PR and needs no recurring manual review, auto-merge service or general repository-reference veto. Ordinary contributor PRs targeting `staging` must pass the required kernel-entry check before merging. A release-specific livepatch or test is something to **remove with** its kernel, not a reason to keep that kernel. Reusable tests run against the stable selector. This plan supersedes the earlier proposed PR workflow. Only local source and Git history have been inspected; nothing has been backfilled, built, run against production or published.

## 1. Policy and metadata

Keep the current format and public imports of `os/packages/linux/available-kernels.nix`. Each `kernels."<key>"` gets `dateAdded = "YYYY-MM-DD";` and optionally `keepUntil = "YYYY-MM-DD";`. No duplicated duration field: express a 90-day hold by adding 90 calendar days to the introduction date and recording the result. Both fields are strict Gregorian UTC calendar dates; a null, malformed/future addition, or hold before introduction is invalid. A hold can extend but never shorten the minimum.

At a supplied UTC instant with date `D`, the **only selection criteria** are:

1. `D > max(dateAdded + 30 calendar days, keepUntil if present)`. Added November 1: retained through December 1, first age-eligible December 2. A `keepUntil` of January 31 is inclusive.
2. The key is **neither** `stableKernelVersion` nor `unstableKernelVersion` (protect both resolved targets, even if identical).
3. No covered production host currently uses that key or its livepatched/native equivalent, with complete fresh evidence as defined below.

All matching entries are removed together; an invalid input or inconsistent edit fails the **run**, rather than adding a retention exemption. No searching the repository or downstream deployments to promote references into holds. Downstream users can set `keepUntil` or stick to an older OS revision when they need a future boot or rollback target not running now.

**Source basis.** At local vpsAdminOS `origin/staging` `b86287c10` there are nine keys, stable **6.12.118** and unstable **6.18.49**. `os/packages/linux/packages.nix` selects the default from `system.vpsadminos.enableUnstable`; `os/modules/config/kernel.nix` supports explicit selection. `flake.nix` exports `lib.availableKernels`, `lib.kernelVersions` and `ci-toplevel-kernel-*`. `.github/workflows/kernels.yml` builds the enumerated matrix. `skills/update-kernel/SKILL.md` points to `docs/os/kernel-updates.md`: registrations edit the catalog; there is no need for a second version updater. Dates are maintenance data, not inputs to Linux/ZFS builds. The existing kernel-build workflow is path-filtered and expensive; it is not the proposed required metadata check.

**Backfill once, then enforce.** At the approved baseline enumerate the keys. For each, verify the structural addition of that **version key** in vpsAdminOS Git history, comparing the introducing tree with its parent(s), following prior file shapes and the rename from `availableKernels.nix` (`77527f4c8`). Use the earliest proven introduction on the maintained branch's ancestry, inspect merges and distinguish removal/restoration from a different identity. Repins, releases of upstream Linux, moving a selector and editing an entry do not reset age. Convert the verified OS commit's **committer epoch** (`%ct`) to a UTC date. E.g. `71ae15a14` added `6.12.48`; `b1f9e8e5c` added `6.18.49` on 2026-10-12 UTC although authored in September. Review the complete `key → commit → date` table at implementation; don't guess on shallow or ambiguous history. No history walk in builds or normal retention runs.

Register new versions with their UTC day added, never a copied predecessor date. Validate the evaluated **whole** catalog: required field per key, permitted fields/types (including misspelled holds), dates and resolved selectors; surviving entries cannot change `dateAdded` outside the explicit migration. Extend `.overcommit.yml` alongside existing Nixfmt/RuboCop to validate the exact **index** (including staged companion files), not the unstaged checkout. Use the same checker in CI and before the maintenance commit. No fleet request at commit time. Inject a UTC evaluation date for date checks; preserve the existing project's hook and commit-message requirements.

**A → hook/CI/D contract.** `python3 tools/kernel-entry-check.py check --as-of YYYY-MM-DD --base <commit-sha> (--tree <candidate-commit-sha> | --index)` validates the whole evaluated Nix catalog. Select exactly one of `--tree` and `--index`. Callers use the exit status, not a JSON/paths interface; diagnostics may name failing keys. D owns machine-readable planning outputs and paths. GitHub dispatch resolves the published candidate ref to the exact SHA, obtains `staging` itself and verifies base ancestry.

### Require kernel-entry validation on incoming PRs

Add a standalone `.github/workflows/kernel-entry-check.yml` with one uniquely named job/check, **`kernel-entry-correctness`**. On every `pull_request` targeting `staging` (including updates, reopens and retargets to that branch), check out GitHub's candidate merge tree, not `staging` alone. Invoke the same offline whole-catalog `check` as Overcommit and the pruner; pass the corresponding base for `dateAdded` immutability. Always run this short job, including on docs-only PRs: no `paths`/`paths-ignore`, skip conditions, or `continue-on-error`. A missing checkout, failed evaluation or invalid field must not produce success. Use a disposable GitHub-hosted runner with `permissions: contents: read`, checkout credentials not persisted, no secrets, fleet request or writes; use `pull_request`, **not** `pull_request_target`. If `staging` uses a merge queue, also run the same check on `merge_group` (`checks_requested`) against the group SHA/base; otherwise don't introduce a queue.

**Enforcement is a repository setting, not a property of YAML.** Land the backfill, validator and workflow first, observe the actual GitHub Actions check name/source, and verify an unprivileged good/bad candidate before an authorized repository administrator makes that exact check required on `staging`. Require it on the current candidate; recheck after a head/base change. Keep the checker/workflow definition under trusted maintainer review (bind the required workflow/source where supported); a same-named unrelated job is not evidence. Do not turn on a blanket PR-only rule just to require this check. Validate the compatible direct-FF route below, including existing scheduled writers, before turning on enforcement; do not relax existing rules. No settings change is part of this plan revision.

## 2. Live usage without production credentials

At vpsAdmin `origin/master` `4062a8da3`, `api/lib/vpsadmin/api/resources/node.rb` (`PublicStatus`), `api/models/node.rb`, and `api/spec/api/resources/node_read_spec.rb` agree with go-client `5934903`, `client/resource_node_action_public_status.go`: anonymous **GET `https://api.vpsfree.cz/v7.0/nodes/public_status`** returns one **unpaginated** list. Require successful HTTP and HaveAPI `status: true`, then `response.nodes`. Rows cover **active DB records of roles `node` and `storage`**, across locations/environments, including stale rows. Anonymous responses omit `id`; use the unique `fqdn`. `status` is false when the current status is absent or more than 120 seconds old. Use `status`, `last_report`, `type`, `hypervisor_type`, `fqdn` and `kernel`. `/nodes` is a different authenticated paginated index (`limit`/`from_id`), with kernel/status redacted for non-admins; don't silently substitute it. No admin token or API changes.

`libnodectld/lib/nodectld/{node_status,system_probes/kernel}.rb` report `/proc/sys/kernel/osrelease`. `6.12.113.1`, for instance, is a numbered livepatch on `6.12.113`. Match exact catalog keys and recognized canonical native-plus-numbered-release forms; protect all established equivalent targets in a collision. Never truncate arbitrary suffixes or compare version prefixes (`.11` is not `.110`). Unsupported grammar, ambiguous identity or a release absent from the current catalog is an error, not evidence of non-use. The separate `vpsfree-cz-configuration` `configs/node/kernels.nix` and `scripts/runtime_kernels.rb` use an ignored local runtime file, explicit overrides and SSH `uname`; do not treat these as a production census or reuse their truncation/error defaults.

Use bounded verified HTTPS, no redirect to another source or cached fallback. Require a nonempty complete set of unique expected identities, recognized role/host type, nonempty release, `status == true` and `last_report` within `[asOf − 120s, asOf]` for **every** covered host; likewise require the acquisition timestamp in that interval. An offline/maintenance machine is not excluded. Known last-seen versions are informative, but any missing/duplicate/stale/unsupported row, API/transport/schema failure or unexpected pagination blocks all writes. Never print response bodies or host identities in public logs.

**Rollout prerequisite, not a claim about production:** ops must reconcile the public population with the machines intended to be covered (including whether inactive/unrepresented machines can actually run these kernels). For autonomous writes configure a trusted expected fleet membership, e.g. a repo Actions variable containing the digest of sorted unique canonical `fqdn` values from the separately reconciled site roster. Define the digest encoding once (lowercase DNS names, strip one trailing dot, sort bytewise, one UTF-8 name and newline per row, SHA-256); reject duplicates before hashing. Compare it on both collections, require ops to refresh it when membership changes, never bootstrap it from the very response being checked. Missing proof, unsupported reports, or legitimate scope beyond the endpoint means report-only until resolved; do not add write-capable/admin credentials to work around it. No raw host list or fleet snapshot in Git.

## 3. Make the deletion set explicit

Inventory **actual consumers** during implementation, not every textual occurrence of a version. Publish one ownership convention in the update/livepatch guides and a validator for it. A key's removal plan consists of the literal catalog binding plus the following **typed** units. Resolve them on the unmodified base and check the whole candidate after deletion. No `grep`-and-delete, arbitrary repo-wide path lists, or code execution supplied by a fleet response.

| Unit | Ownership and deletion |
|---|---|
| **Numbered livepatches** | `os/livepatches/batches/<K>/` is already the authoritative root (discovered by `os/livepatches/lib.nix`). Remove the **entire stack** for `K`, including every ordinal, descriptor, series, fix, patch, qualification manifest, helper, oracle and validator. Remove the release-specific `docs/os/livepatches/<K>.md` and its exact navigation entry in `mkdocs.yml`; preserve process/template and older Git history. Packages, qualification rows, matrix entries and runner instances derived from the remaining catalog must disappear/recompute automatically. Never transplant a patch to stable or leave a dangling predecessor. |
| **Kernel-specific tests** | Use `tests/kernel-specific/default.nix { lib }` to discover canonical version-keyed roots `tests/kernel-specific/<K>/default.nix { kernelVersion }`, with optional `runnerTests` and `checks`. Keep private boot config, assertions, data and helpers within the directory. A catalog key may have no test registration; the reverse (orphan registration) is invalid. The empty registry must evaluate. `tests/all-tests.nix`/flake checks discover only these registered units; keep shared templates outside. Prune by removing the registered directory (empty registrations are valid). Numbered livepatch oracles/tests already owned by a batch stay there, not in two registries. No weekly editing of arbitrary test bodies, `flake.nix` or workflow files. A validator rejects a unit with no catalog owner, unsafe path or duplicate ownership. |
| **Legacy/range livepatches and payload files** | `os/livepatches/available-patches.nix` has a cumulative rule matching `[6.12.48, 6.12.89)` with a named patch. `os/livepatches/ebpf/available.nix` has program names, enable flags and kernel ranges, e.g. `ptrace_mm_guard`. Use their **evaluated target predicates** over catalog keys before and after the batch removal. For each matching deployable payload that loses its last target, remove its exact named registry record and exclusively owned source(s)/tests. Keep a matching shared payload intact while **any** supported target remains. Don't delete generic infrastructure, open-ended examples or unrelated preexisting orphans as a side effect; don't infer targets from filenames. Declare any non-derivable shared/exclusive auxiliary paths in the owning unit and validate no remaining owner before deleting. |
| **Packaging** | Removing the catalog binding removes its Linux/ZFS pin/configuration. Preserve shared files (e.g. a ZFS patch used by several surviving tuples). Account for genuinely version-private package data such as the `6.12.109` conditional patch in `os/packages/linux/default.nix`: bind it to a structured per-version package record in preparation, preserving application point/order and all builder paths; remove that named record and its private patch when the version goes. No cache GC, Linux/ZFS source-ref deletion, Git history rewriting or deployed livepatch unload. |

For discrete Nix/UI navigation bindings use exact structural edits (or scoped discovered directories for new ownership); do not implement a general Nix rewriter. Use an available syntax-aware editor for the few literal bindings, or refactor affected bindings into import-per-record discovery in the preparatory change if a reliable editor is unavailable. Preserve selectors, comments of retained entries and all unrelated tuples. Constrain all deletion paths to tracked, typed roots with canonical components, no symlink traversal or globs supplied by metadata. Reject an unexpected diff. Ownership affects the *contents of the transaction*, never eligibility.

### Instructions for future tests

Update vpsAdminOS **`AGENTS.md` → Testing Guidelines** and **`docs/os/testing.md` → Writing a test**: VM tests inherit the stable kernel by default. Derive expected release/ABI from the stable selector and selected package, never from a literal or from whatever `uname` happens to return; keep the guest assertion meaningful. Cite **Stable-kernel NFS cancellation CI** as the example. Mark the `boot.kernelVersion = "6.1.30";` example under **Temporary config changes** as a local diagnostic override, not a committed suite pattern (or illustrate it with a non-kernel option). Exact-target livepatch tests and rare, well-justified release-specific regressions may pin: document the exact target, why stable cannot test the property, which registration owns its private files and that they retire with the kernel. A short reason beside the registration and code review suffice; no general source scanner, evergreen test pin or retention exemption. Preserve the separate userspace upgrade-test lifecycle guidance.

## 4. Plan, apply, verify, push

Use a small maintainer CLI with separate operations: `check` (index or tree, offline); `collect` (minimal timestamped projection of the one action); `plan` (pure); `apply` (apply only a verified plan to a clean disposable checkout). Give `plan` the base revision, explicit UTC instant, fleet projection and trusted membership digest. Sort decisions and owned paths bytewise. The same inputs yield the same reasons, keys and diff on replay with **no** network/implicit clock. Dry run by default; failure is distinct from an empty successful result. Intermediate full projections are private, short-lived. Log base, time, versions/reasons, aggregate coverage and changed paths, not identities or secrets.

1. Weekly cron on the trusted `vpsfreecz/vpsadminos` repo, optionally manual dispatch constrained to `refs/heads/staging`. Check out the current remote `staging` SHA **B** (not a caller-specified feature SHA). Serialize retention runs; other maintainers and scheduled update jobs can still advance the branch. Collect fleet evidence, plan on B. On any failure exit nonzero without a write; on zero candidates exit successfully without an empty commit.
2. Apply the exact deletion set in a clean temporary checkout based on B, run the same hooks/formatter/catalog checks as contributors, create **one local commit C whose only parent is B**. Independently compare actual `B..C` to the planned diff. Run the offline verification below on the exact C tree before granting any push. Tests must confirm all and only the candidate units disappeared; don't rely on an eventual push-triggered CI. Stage only scoped paths; `git commit -F` with the maintenance rationale. No raw evidence in the commit. A successful job on B (including the scheduler's own run) is **not** the required GitHub check on C.

   **Exact-SHA admission for direct pushes.** For normal human fast-forward integration, run `kernel-entry-correctness` on the exact published development head to be pushed (e.g. `workflow_dispatch` of the same read-only workflow on that ref). For a protected weekly push, publish the checked C on an isolated run-owned candidate ref without touching `staging`, dispatch the **same** check on that ref and verify GitHub reports success from the expected source **on C**. Dispatch using a bounded trusted orchestration job with `actions: write` only if needed; the check itself remains read-only. For dispatch, compare to the actual `staging` baseline and verify C descends from it, not an arbitrary caller-supplied baseline. Don't rely on a `GITHUB_TOKEN` candidate-ref push to trigger checks. If an acceptable exact-SHA check already exists, reuse it. No PR, standing actor bypass, synthetic success status or check on a different SHA. Prove the selected route works with the actual `staging` rules; if not, stop before enforcement/writes and resolve the rule conflict with the administrator. Ordinary human integrations still need their usual approval.
3. After the required check passes, immediately before the `staging` push, reread the remote tip; require it still equals B. Collect a **second**, newly acquired production snapshot, recompute on **B, not C**, at a fresh UTC instant; require the exact same eligible keys/owned changes as the tested commit, same coverage, freshness and no changed inputs. If anything differs or too much time elapses, discard this attempt; restart from a fresh base/plan later rather than force, blindly rebase or push a subset. Push C to `refs/heads/staging` with an ordinary **non-force** `git push`, never `--force`/`--force-with-lease`; a concurrent forward push makes C non-fast-forward and is rejected. Re-read the resulting ref/ancestry if the push result is uncertain; no blind retry. **No PR is opened.**
4. `contents: read` by default; `contents: write` only for trusted maintenance ref publication/FF, no PR permission, admin credential or production secret, no fork/PR code in that writer. A read-only prepare/check job can pass the checked commit via a run-local Git bundle, binding B/C and tree digest; the writer verifies parent, tree and scoped diff before freshly planning/pushing. No network credentials during candidate code checks. Verify branch rules allow this exact automation principal's ordinary FF push. Don't disable protections or broaden tokens to evade an incompatible ruleset: leave report-only until ops configures permitted access. `.github/workflows/{daily-update,flake-update}.yml` provide direct-push precedents; `GITHUB_TOKEN`-authored pushes do not automatically trigger normal push workflows. Run the required offline checks in this workflow explicitly; preserve the existing scheduled kernel-build matrix. Verify imported action versions at implementation time.

The final double check narrows the race; a Git update is **not atomic** with a node boot. Ops should suspend the schedule or set calendar holds during transitions that can introduce an old kernel (including rollbacks). This isn't a per-run permission step. Report-only trials establish deployed response shape, normalization and population **before enabling writes**; direct weekly writes are the intended end state.
